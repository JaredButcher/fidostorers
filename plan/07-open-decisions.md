# Open decisions

Things this plan made a reasonable default call on, now deliberately confirmed or
overridden rather than left to ossify by momentum.

## Decided

| # | Decision | Outcome | Notes |
|---|---|---|---|
| 1 | FIDO transport crate | [`authenticator`](https://crates.io/crates/authenticator) 0.5.0 (Mozilla) — **kept, with a known Windows limitation** | The premise of this row was wrong. This crate has **no `webauthn.dll` backend**; its Windows path is raw USB HID via SetupAPI, the same as Linux. Salt-based `hmac-secret` *is* fully plumbed through (`HMACGetSecretInput`/`HMACGetSecretOutput`, used identically on both OSes) and Windows hardware testing confirms it works. But Windows 10 1903+ denies non-elevated read/write opens of FIDO HID devices, and M1's test 3 confirmed that bites: **all device interaction requires an elevated terminal** (`list` works unprivileged; `register`/`derive`/`selftest` do not). **Accepted for now** rather than switching transports — the fallback (keep this crate on Linux, add direct `webauthn.dll` FFI on Windows) is deferred to phase 2, [06-roadmap.md](06-roadmap.md). Also note the crate does not compile for Windows as published; see the `winapi` shim in the workspace manifest. |
| 2 | Crate names | `fido-token` / `fidostorers` | Confirmed for the workspace. Revisit only if publishing: `fido-token` is generic enough that crates.io may want `fidostorers-token`. |
| 3 | Vault file extension | `.fido` | Confirmed. Chosen over `.fstr` (matches the `FSTR` magic) and `.vault` on the grounds that the extension's job is to tell a human browsing a directory how to open the file, and "use your security key" is the useful signal. The magic bytes stay `FSTR` regardless — extension and magic need not match. |
| 4 | AEAD cipher | XChaCha20-Poly1305 | Confirmed. The 192-bit nonce is what makes random-per-write nonces safe with no counter state, which matters because KV mode re-encrypts the whole payload on every `set`/`rm` under a data key fixed for the vault's lifetime. See the nonce discipline section of [03-vault-format-and-crypto.md](03-vault-format-and-crypto.md). |
| 5 | Header/vault serialization | `postcard` over `serde`-derived structs | Chosen over a hand-rolled encoder. The usual objection — that AAD bytes must stay reproducible across encoder versions — does not apply here, because there is no AAD (see below) and `header_mac` is computed over the literal bytes written to disk and verified over the literal byte range read back. The header is never re-serialized for authentication. **Still required**: explicit parse-time bounds on `credential_count`, `rp_id` length, and every length-prefixed byte string, checked before allocating, since length prefixes are read from an unauthenticated file. |
| 5b | Header authentication | **No AAD anywhere; single `header_mac`** | New decision, resolving a contradiction between docs 02 and 03. Every AEAD call passes empty associated data; header integrity comes from `HMAC-SHA256` over the header under a key HKDF'd from the data key. Rationale and the full field-by-field accounting are in [03-vault-format-and-crypto.md](03-vault-format-and-crypto.md) "Header authentication". The load-bearing reason: header-as-AAD would make each credential's wrap depend on every other entry, so revoking a lost key while holding the primary would silently brick a backup key in a safe. Consequence: `Vault::revoke` now takes the data key. |
| 6 | `rp_id` value | Configurable per-vault, default `"fidostorers.local"` | Upgraded from "fixed constant" — costs nothing, the field already exists on `Vault`, `Credential`, and `init --rp-id`. The default works against real hardware on Windows through the raw-HID backend (M1 tests 2 and 4). Whether `webauthn.dll` accepts a non-domain rp_id from a native (non-browser) caller is untested and moves to the deferred phase-2 backend work. |
| 7 | Resident vs. non-resident credentials | non-resident (v1) | Confirmed, no change. Deferred per [04-security-and-threat-model.md](04-security-and-threat-model.md). |
| 8 | Directory-mode symlinks & permissions | Preserve in the archive; best-effort on extract | The tar always stores symlinks as symlink entries and real Unix mode bits, on every OS, so a vault written on Linux round-trips back to Linux with full fidelity no matter where it was stored in between. Extraction applies what the platform allows. On Windows, symlink creation needs Developer Mode or elevation, so a failure warns per-entry (naming the link and its target, and how to enable it) and continues; Unix mode bits are ignored with a single warning. Rejected: dereferencing symlinks at seal time, which is lossy, duplicates bytes, needs cycle detection, and would drop executable bits on scripts. Also rejected: hard-failing extraction, which blocks Windows users entirely on any vault containing a symlink. **Extraction that skipped anything must exit non-zero** with a distinct code, so scripts can detect an incomplete tree rather than trusting a silent success. **Implemented in M3** as exit code 20, carried by an `ExtractReport` return from `open_dir` (`()` could not express it). The Linux side is covered by tests; the Windows symlink-refusal path is exercised only synthetically and still needs a real Developer-Mode-off check — see [06-roadmap.md](06-roadmap.md) M3. |
| 9 | PIN input mechanism | Library takes an optional callback (`PinProvider`); CLI uses `rpassword` | Confirmed, but **the stated Windows asymmetry does not exist**: it followed from the belief that Windows went through `webauthn.dll`, and it does not (#1). With a raw-HID backend on both OSes, our callback fires on Windows too and the OS renders no dialog of its own. Keeping it `Option<...>` remains right — `None` means "refuse rather than prompt", which is what `--no-pin` and non-interactive stdin need — but no code path should assume it *fails* to fire on Windows either. **Confirmed by hardware test 6 on Windows**: our own no-echo prompt is what appears, and `--no-pin` refuses cleanly. |
| 10 | Workspace layout | `crates/fido-token`, `crates/fidostorers` | Already implemented; top-level `src/` is gone. Nothing left to decide. |

## Still open

**Nothing is blocking.** #1's deciding test has been run: `fido-token selftest`
**fails** in a non-elevated Windows terminal and **passes** when elevated — the
`FAIL`/`PASS` row of test 3's table. Requiring Administrator on Windows is accepted as
a known limitation for now, so the transport stays as chosen and the `webauthn.dll`
backend is a **deferred phase-2 task**
([06-roadmap.md](06-roadmap.md)), not required work. It should be revisited before any
release aimed at non-developers.

#9's Windows asymmetry has been **withdrawn** as a consequence of the same finding,
and test 6 confirmed the withdrawal.

Unverified rather than open: **Linux hardware testing has not been run.** The same
procedure ([../docs/M1-MANUAL-TESTING.md](../docs/M1-MANUAL-TESTING.md)) must pass
there before M1 closes. Nothing in the Windows result predicts a Linux problem —
Linux gates the same access behind udev rules rather than a filter driver — but it is
currently untested, so no claim is made about it.

Nothing is open. #8 governs M3 and #5/#5b govern M2, both ahead of the milestones that
need them; #15–#20 govern M7–M11.

## New decisions from M1

| # | Decision | Outcome | Notes |
|---|---|---|---|
| 11 | Hardware backend gating | Default-on `hardware` cargo feature | The `authenticator` dependency needs pkg-config + libudev headers on Linux. Putting it behind a feature keeps the hardware-free suite — which [05-testing-strategy.md](05-testing-strategy.md) promises runs everywhere — buildable on machines that cannot supply them, and lets crate 2 be tested without the platform HID stack. With the feature off, `HidAuthenticator` returns `TokenError::BackendUnavailable`. |
| 12 | Device enumeration | Implemented in-crate, not via `authenticator` | The crate exposes no public enumeration API, and its discovery is entangled with running a real operation (which needs a touch). Listing must be passive, so it is implemented against sysfs (Linux) and SetupAPI (Windows). Consequence: capabilities cannot be reported without a CTAP2 `getInfo`, which needs an I/O open, so `supports_hmac_secret`/`supports_client_pin` became `Option<bool>` and are `None` from enumeration. `selftest` is the authoritative capability answer. |
| 13 | Secret logging | Never the bytes; a truncated-hash `fingerprint` instead | Debugging a derivation mismatch requires knowing *whether two derivations agree*, which a fingerprint answers without putting key material in a log file. Salts are logged in full — they are not secret ([03-vault-format-and-crypto.md](03-vault-format-and-crypto.md)) and are the other half of what makes a mismatch diagnosable. PINs are never logged. |
| 14 | Client data hash | Fixed domain-separated constant | CTAP requires 32 bytes to sign over. There is no relying party and the signature is never checked — only the hmac-secret output, which does not depend on this value — so a constant keeps operations reproducible and removes a needless RNG dependency from the derive path. |

## New decisions for interactive mode

Taken before planning [08-interactive-mode.md](08-interactive-mode.md) and
[09-credential-encoding.md](09-credential-encoding.md), because each one changes what
those documents say rather than merely how they say it.

| # | Decision | Outcome | Notes |
|---|---|---|---|
| 15 | What "open" means for `file`/`dir` stores in a session | **Plaintext working directory on disk** — *implemented in M10* | An opened store is extracted to a working path so ordinary tools (editor, file manager, `grep`) work on it; closing re-seals and removes it. Chosen over holding the tree in memory (no plaintext on disk, but unusable with outside tools) and over write-through (crash-safe, but then "lock on exit" has nothing to do). **This is the largest security change in the project so far** — it puts unencrypted user data in the filesystem for the life of the session — and [08-interactive-mode.md](08-interactive-mode.md) is written around containing it: runtime-directory placement, `0700`, an idle timeout that actually re-seals, orphan recovery, and an explicit statement that deletion is unlinking rather than secure erasure. `kv` stores need no working directory and stay memory-only. |
| 16 | Vault write sequence | **Unchanged** — temp file, fsync, rename over the original | The originally requested sequence was write `<vault>-tmp.fido`, delete the original, then rename. That is strictly weaker than what M2 already implements: `rename(2)` over an existing path is atomic on Linux and on Windows for same-volume moves, so the vault path currently holds either the complete old file or the complete new one at every instant, whereas delete-then-rename opens a window where the path does not exist at all and recovery needs a documented manual step. Reviewed and left alone. The only property the requested scheme would have added is a *predictable* temp filename; the cost is a real crash window, and the existing `tempfile` name is cleaned up automatically on every path except a hard kill. |
| 17 | Scope of hex credential IDs | **CLI JSON only; vault format untouched** | `fido_token::Credential` is serialized both to JSON by the CLI and by postcard into every vault header, and serde attributes are per-type rather than per-format — so encoding the field as hex on the type itself would also change the on-disk header, doubling that field's size and forcing `FORMAT_VERSION` 2 plus a migration for existing vaults. A separate `CredentialJson` DTO in the CLI gets the readable output with no format change at all. See [09-credential-encoding.md](09-credential-encoding.md). |
| 18 | Session key lifetime | **Idle timeout, on by default (15 min)** — *implemented in M9* | `--idle-timeout 0` disables it. Chosen over an unbounded session so that interactive mode does not quietly become an always-unlocked vault on an unattended machine. Two consequences the plan has to carry: expiry performs a *full* close (re-seal, remove plaintext, drop keys), because dropping the key while leaving an extracted tree on disk would report "locked" while the data stayed readable; and activity counts modifications inside a working directory, not just REPL commands, or a user editing files elsewhere for twenty minutes would have the tree sealed out from under their editor. **M9**: the first consequence is implemented — expiry does a full close, dropping the key and releasing the vault's lock — and a warning fires 60 seconds ahead by default. The second is moot until M10 gives a store a working directory to watch; today only REPL commands count as activity, because they are the only activity there is. |
| 19 | Interactive shutdown gesture | **Ctrl+D exits; Ctrl+C cancels** — *implemented in M9* | Reversed from the original request after review. Every common REPL — `python`, `psql`, `irb`, a shell — treats Ctrl+C as "cancel this line or operation" and Ctrl+D as end-of-input, and a user who reflexively hits Ctrl+C to clear a half-typed command should not have their session end. It also frees Ctrl+C for the job it does best: interrupting a shutdown that is taking too long, which the seal sequence explicitly supports. `exit`/`quit`, EOF, `SIGTERM` and `SIGHUP` all run the same graceful path. **M9**: implemented, with two limits recorded in [06-roadmap.md](06-roadmap.md) M9 — Ctrl+C cancels an unlock between candidate factors rather than mid-touch or mid-Argon2, and on Windows there is no SIGINT handler, so `rustyline` covers Ctrl+C at the prompt while a Ctrl+C during an operation ends the process. |
| 20 | Second authentication factor | **Keyfile + password, both required, Argon2id** | A factor that needs no hardware, enrolled and revoked like a security key. Both inputs are mandatory: a keyfile alone would be a copyable bearer token (strictly weaker than a security key, whose secret cannot be copied), and a password alone is exactly the offline-guessable secret this project set out to avoid. Derivation is `Argon2id(password, salt = the entry's existing 32-byte salt, secret = SHA-256(keyfile))` then the usual HKDF with its own `info` string. Three sub-decisions are load-bearing and are argued in [10-keyfile-password-auth.md](10-keyfile-password-auth.md): the keyfile goes in Argon2's `secret` (pepper) input rather than being concatenated; **no keyfile fingerprint is stored**, because it would let a vault-file holder test candidate keyfiles offline without the password; and Argon2 cost parameters are capped at parse time exactly like the header's length prefixes (#5), since they too are read before authentication and drive an allocation. **The cost is real**: a vault is only as strong as its weakest enrolled factor, so adding this to a vault lowers it, and "there is no password to brute-force" stops being true. See [04-security-and-threat-model.md](04-security-and-threat-model.md). |

## New decisions from M9

| # | Decision | Outcome | Notes |
|---|---|---|---|
| 21 | How the REPL reuses the one-shot CLI | **Shared argument *groups*, not the subcommand enum** | [08-interactive-mode.md](08-interactive-mode.md) asked for the existing `clap` definitions to be reused so the two spellings cannot drift. Reusing `Commands` wholesale was rejected: a REPL command names an **open store** rather than a path, and carries no unlocking flags at all, so `kv set <vault> --keyfile ...` inside a session would advertise doing again the very thing the session exists to do once. What is shared is every argument group whose meaning is unchanged — `AuthArgs`, `Argon2Args`, `KvValueSource`, `AuthKind`, `Mode` — so a flag cannot mean two different things and `open`'s help text is `AuthArgs`' own. |
| 22 | Scope of the advisory lock | ~~Writers only~~ → **Everything, while a session holds the vault** (revised in M10) | M9 reasoned that excluding readers bought nothing, because reading cannot corrupt a vault and `Vault::write`'s rename (#16) means a reader sees either the whole old file or the whole new one. **M10 makes that wrong.** A session now holds a working directory whose edits are not in the vault file until it is sealed, so a reader gets a version that is about to be replaced, and reporting it as the vault's contents is worse than refusing. The requirement is now explicit: *while a session has a vault open, no other `fidostorers` process may open or write it.* Implemented as two operations rather than one lock mode — writers `acquire` (exclusive, creating the file), readers `ensure_available` (checking without taking) — so concurrent readers still never block each other, and a process never excludes itself. |
| 23 | Clearing a lock whose holder may be gone | **Only when provably dead; otherwise `--force`** | A lock is cleared automatically only if it names this host *and* no such process exists. "I cannot tell" is not staleness — another machine's pid, or a platform with no liveness check — and neither is a lock file too corrupt to parse; both require `open --force`, which is itself the user's confirmation. Liveness comes from `/proc` on Linux; Windows would need `OpenProcess`, i.e. a dependency taken purely to spare the user one `--force`, so it answers "unknown". Guessing "dead" when we cannot check would steal a live session's lock, which is the one outcome that loses data. |
| 24 | Session history | **Structurally in-memory, not merely unsaved** | `rustyline` is declared with `default-features = false`, which drops `with-file-history` and makes `DefaultHistory` an in-memory type with no method that reaches disk. plan/08 requires memory-only history because `kv set --value <secret>` would otherwise be persisted in cleartext; a type that *cannot* write is a better guarantee than remembering never to call `save_history`. |
| 25 | `--stdin` and `--password-stdin` inside a session | **Refused where stdin is the prompt** | `kv set --stdin` would read to EOF from the terminal the user is typing at, consuming the rest of their input, so it is rejected outright with a pointer to `--file`. `--password-stdin` is rejected only when stdin is a *terminal*, where it would read an echoed line and defeat the no-echo prompt it exists alongside; piped input is the scripting case it was built for and still works. |
| 26 | What `info` claims inside a session | **Authenticated there, unauthenticated one-shot** | Opening a store unwraps the data key and verifies `header_mac` with it, so a session really has checked what the touchless one-shot `info` cannot (#5b, plan/04). Both callers share one printer that takes an `authenticated` flag rather than duplicating the output, because the difference between the two is a genuine change in guarantee and printing "UNAUTHENTICATED" in a session would be a lie in the safe direction. |

## New decisions from M10

| # | Decision | Outcome | Notes |
|---|---|---|---|
| 27 | Detecting whether a store needs sealing | **Digest of the bytes a seal would write** | plan/08 sketched a manifest of path, size and mtime, with a hash for `file` mode. Replaced by one mechanism for both modes: `SHA-256` of exactly the payload a seal would produce — the file's bytes, or `archive::build`'s deterministic tar. It answers the actual question ("would sealing change the vault?") rather than approximating it, it cannot miss a change that preserved size and mtime, and it hands back the payload it just built, so a dirty store is sealed without walking the tree twice. The baseline is the tree **as extracted**, not the archive it came from, because extraction does not restore mtimes and every rebuilt header would otherwise differ. |
| 28 | What `stores` shows in its dirty column | **A cheap stat scan, not the exact answer** | The exact check reads every byte, and a status display must stay instant on a large tree. So `stores` walks stat metadata only and may say "changed" for a tree that would seal to identical bytes. The direction of the error is the safe one, and the display never decides anything: the write is decided by the exact digest at seal time. |
| 29 | A seal that fails | **Keep the plaintext; do not remove the working directory** | Closing normally removes the working directory. If the seal failed, that tree is the *only* copy of the user's changes, and deleting it would turn a write error into data loss. The store keeps its plaintext, the path is printed, the session exits non-zero, and the tree becomes an orphan the next session offers back. The same rule covers a shutdown interrupted by Ctrl+C: whatever was not reached keeps its plaintext. |
| 30 | Secure erasure of working directories | **Explicitly out of scope** | Removing a working directory is `unlink`. On an SSD, a CoW filesystem, or any journalling filesystem, that does not reliably destroy the prior contents, and no amount of overwriting from userspace changes it. Rather than implement a gesture that would only look like a guarantee, this is stated as a non-goal: users who need plaintext never to reach stable storage keep the working directory on a tmpfs or ramdisk. The default location already is one on Linux (`$XDG_RUNTIME_DIR`), and `--work-dir` exists to point elsewhere. |
| 31 | Idle activity from outside the REPL | **Stat scan every 5 seconds, not every tick** | plan/07 #18 requires edits inside a working directory to count as activity, or a user editing files in another window would have the tree sealed out from under their editor. The scan walks every open tree, so it runs far less often than the clock check; five-second granularity is irrelevant against a fifteen-minute timeout, and the visible cost is that a countdown can restart a few seconds after an edit rather than instantly. |
| 32 | Where a session records what it has open | **A JSON record per pid, beside the working directories** | Orphan recovery needs to survive the process, so the record cannot live in memory, and it is rewritten whenever the open set changes rather than only at startup — a crash at any moment then leaves a record matching what is actually extracted. It is placed under the same runtime root as the working trees, so a machine that clears that root on reboot clears both together. Only records this host wrote, whose pid is *provably* dead, are offered: the same conservative rule as #23, because offering to seal or discard a directory a live session is still editing would be the one mistake that destroys data. |

## New decisions from M11

| # | Decision | Outcome | Notes |
|---|---|---|---|
| 33 | How a data key is pinned | **A page-aligned allocation per key, not an `mlock` of an existing value** | Two reasons, either sufficient. `mlock`/`munlock` act on whole pages, so two secrets sharing a page would mean unlocking one silently unlocked the other. And locking the address of an ordinary `Zeroizing<[u8; 32]>` would pin a page the value is free to be moved out of — Rust moves by `memcpy` and the lock does not follow. `SecretKey` owns a stable, page-sized allocation the bytes never leave, locked *before* the secret is written into it, zeroized before release. Costs 4 KiB per open store. |
| 34 | What `Vault` takes for a data key | **`&[u8; 32]`, not a particular wrapper** | A one-shot command holds its key in a `Zeroizing`; a session holds it in a locked `SecretKey`. The vault should not care, and does not need to: deref coercion meant changing the parameter type left every existing call site compiling unchanged. Same reasoning that keeps `unlock_with` taking an already-derived KEK rather than talking to hardware. |
| 35 | Scope of core-dump suppression | **Every command, not only sessions** | Memory pinning is session-scoped because that is where the plan located the risk — a key held for one command is unlikely to page out. A crash dump is different: it captures whatever is live at that instant, so the exposure is the same for a one-shot command, and the call costs nothing. Applied once in `main`, before any key exists, so there is no window in which a dump would have contained one. |
| 36 | Claiming hardening vs. measuring it | **Probe, then print the real status** | `mlock` can fail on `RLIMIT_MEMLOCK`, and Windows cannot suppress dumps at all. Rather than a doc sentence that is true on the author's machine, each measure is attempted and its outcome shown at session startup, with an explicit warning when one is not in force. "We tried to lock memory" and "memory is locked" are different claims and only the second is worth making to someone deciding whether to trust a session. |
| 37 | Windows core dumps | **Reported as unavailable, not attempted** | Crash dumps are configured by the system (WER, or a registered post-mortem debugger) and a process cannot opt out. `WerRegisterExcludedMemoryBlock` could exclude specific pages but does not exist before Windows 10 1709 and would need dynamic resolution — untestable from this development environment, and shipping unverified FFI for a security measure is worse than naming the gap. `VirtualLock` *is* implemented, so pinning works on Windows. |
